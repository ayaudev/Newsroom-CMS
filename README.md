# Newsroom CMS

Университетский MVP на существующем React/Vite frontend и Express backend. База данных — PostgreSQL. Старые маршруты /api/news сохранены; /api/posts предоставляет тот же публичный API.

## Что добавлено

- PostgreSQL: users, posts, categories, comments, post_likes, comment_likes, favorites; внешние ключи, ограничения и индексы.
- Post, Category, Comment и User repositories с параметризованными SQL-запросами.
- Публикации по умолчанию создаются черновиками; публичные маршруты показывают только published.
- GET /api/posts/latest: сортировка по publishedAt DESC, пагинация, поиск и категории; limit от 1 до 100.
- Комментарии pending / approved / rejected. На сайте видны только одобренные комментарии опубликованных материалов. Изменение текста сбрасывает статус в pending.
- Админка: статистика, публикации, категории и модерация; административные API защищены ролью admin.
- Русский интерфейс, даты, роли, статусы, сообщения, адаптивный дизайн, локальные заглушки изображений, безопасный HTML.

## Запуск с установленным PostgreSQL

Требуются Node.js 20+ и PostgreSQL. Создайте отдельную базу newsroom (через pgAdmin или psql), не используйте существующую базу с чужими таблицами.

1. Скопируйте backend/.env.example в backend/.env.
2. Укажите DATABASE_URL и собственный JWT_SECRET. Учётные данные администратора вводятся интерактивно, в .env они не хранятся. Пример URL: postgresql://user:password@localhost:5432/newsroom. Специальные символы пароля в URL должны быть URL-кодированы.
3. В каталоге backend выполните:

~~~powershell
npm install
npm run migrate
npm run setup:admin
npm run seed:demo
npm run dev
~~~

seed:demo необязателен. Создаёт пять опубликованных материалов и один черновик, используя первого существующего администратора (либо ADMIN_EMAIL, если переменная задана явно). Скрипт не удаляет существующих пользователей или публикации.

4. Во втором терминале, в frontend:

~~~powershell
npm install
npm run dev
~~~

Откройте http://localhost:3000. Войдите по электронной почте и паролю, введённым в setup:admin; панель управления: http://localhost:3000/admin. Vite проксирует /api и /uploads на localhost:5000. Для другого хоста API задайте VITE_API_URL в frontend/.env; сервер должен также отдавать /uploads с доступного адреса.

## Первоначальная настройка администратора

После npm run migrate выполните из каталога backend:

~~~powershell
npm run setup:admin
~~~

Команда запрашивает имя администратора (поле name существующей модели), электронную почту, пароль и подтверждение. Вход осуществляется по электронной почте. Имя — от 1 до 50 символов; почта проверяется и приводится к нижнему регистру. Пароль — минимум 12 символов и максимум 72 байта UTF-8; пробелы внутри пароля сохраняются. Оба ввода пароля скрыты, история ввода отключена. Перенаправление stdin/stdout запрещено. Ctrl+C отменяет ввод и восстанавливает терминал без сохранения данных.

Пароль хешируется bcrypt с work factor 12. Эта же политика длины применяется при создании дополнительных администраторов и изменении пароля администратора. Открытый пароль и подтверждение не сохраняются, не выводятся и не передаются через аргументы CLI. Роль ADMIN хранится как admin для совместимости с существующими пользователями, JWT и React-интерфейсом.

Если хотя бы один администратор уже существует, команда завершается с ошибкой до запроса данных. Она не меняет пароль существующего пользователя и не повышает его роль. Проверка и вставка выполняются в транзакции с блокировкой таблицы users: из двух одновременных запусков успешно завершится только один. При занятой почте создание отменяется. Для действующего проекта со своим администратором пропустите setup:admin и используйте существующий аккаунт.

## Вход, выход и доступ

Вход: POST /api/auth/login с email и password. Все аккаунты используют существующую авторизацию JWT; подпись ограничена HS256, срок действия задаёт JWT_EXPIRE. Каждый вход выдаёт отдельный токен. Роль для проверки доступа считывается из PostgreSQL, а не из JWT или localStorage. При обновлении страницы React проверяет текущую сессию через /api/auth/me.

Выход: POST /api/auth/logout с Authorization: Bearer JWT. Сервер сохраняет SHA-256 отпечаток токена в revoked_tokens; сам токен не сохраняется. После успешного выхода повторное использование токена возвращает 401, в том числе после перезапуска API. Затем браузер очищает свою сессию. Другие активные входы остаются действующими. Если сеть недоступна, интерфейс сообщает об ошибке выхода и позволяет повторить запрос.

Без авторизации административные API возвращают 401; обычному пользователю — 403. Публикации, категории, модерация, загрузка изображений и создание дополнительных администраторов защищены ролью admin. Публичная регистрация не позволяет передать административную роль.

Миграция авторизации добавляет revoked_tokens и её индекс; отдельная миграция пользовательских публикаций описана ниже: пользователи, публикации, категории, комментарии и избранное сохраняются. После обновления обязательно выполните npm run migrate перед запуском API.

## PostgreSQL через Docker

Запустите Docker Desktop. Скопируйте корневой .env.example в .env, задайте POSTGRES_PASSWORD, затем из корня:

~~~powershell
docker compose up -d
~~~

В backend/.env укажите DATABASE_URL=postgresql://newsroom:YOUR_PASSWORD@localhost:5432/newsroom. Далее выполните миграцию, seed и запуск по инструкции выше. Данные сохраняются в Docker volume newsroom_pg. Порт 5432 должен быть свободен.

## Перенос существующей MongoDB

Исходная MongoDB не изменяется. Экспортируйте коллекции users, news и comments в отдельную папку, например с mongoexport --jsonArray, в файлы users.json, news.json, comments.json. Если комментариев нет, используйте comments.json с пустым массивом []. Экспорт пользователей должен содержать исходные bcrypt-хеши password.

После npm run migrate в backend:

~~~powershell
npm run import:mongo -- C:\path\to\export
~~~

Импорт выполняется одной транзакцией, сохраняет URL публикаций, хеши паролей, авторов, ответы, просмотры, лайки и избранное. MongoDB ObjectId преобразуются в стабильные UUID. Повторный импорт не перезаписывает содержимое существующих записей. Комментарии без статуса получают pending для проверки редактором. При конфликте email/slug или повреждённых ссылках весь импорт отменяется; исправьте экспорт и повторите. Копировать backend/uploads не требуется при работе в том же проекте.

## API

| Маршрут | Назначение |
|---|---|
| GET /api/posts/latest | Последние опубликованные материалы; page, limit, category, search, tag |
| GET /api/news | Совместимость с прежним frontend |
| GET /api/categories | Категории и число опубликованных материалов |
| GET /api/admin/stats | Статистика редакции |
| GET/POST /api/admin/news | Список и создание публикаций |
| GET/PUT/DELETE /api/admin/news/:id | Просмотр, изменение, удаление |
| GET/POST /api/admin/categories | Категории |
| DELETE /api/admin/categories/:id | Удаление неиспользуемой категории |
| GET /api/admin/comments?status=pending | Очередь модерации с пагинацией |
| PATCH /api/admin/comments/:id/status | JSON: {status: approved или rejected или pending} |
| POST /api/news/:id/comments | Комментарий; content, необязательный parentCommentId |
| POST /api/auth/login | Вход по email и password |
| POST /api/auth/logout | Отзыв текущего токена и выход |
| GET /api/health | Проверка API и соединения с PostgreSQL |

Административные запросы требуют Authorization: Bearer JWT. Публичная регистрация всегда создаёт user независимо от переданного role. Первого администратора создаёт setup:admin. Команда seed сохранена как совместимый псевдоним этого интерактивного процесса. Создание дополнительных администраторов через /api/auth/register-admin доступно только существующему администратору.

## Проверки

~~~powershell
# backend
npm test
npm run test:integration
# frontend
npm run build
~~~

npm test проверяет валидацию администратора, скрытый ввод и подтверждение пароля, повторный ввод, отмену Ctrl+C, отказ при неинтерактивном терминале и безопасную обработку HTML. Интеграционные тесты запускаются отдельной командой.

test:integration использует установленный PostgreSQL 18 в C:/Program Files/PostgreSQL/18/bin (или POSTGRES_BIN). Создаёт изолированный временный кластер на localhost:55439, проверяет интерактивное создание администратора, bcrypt-хеш, блокировку повторного и конкурентного setup, занятую почту, вход, отзыв JWT, права всех административных маршрутов, жизненный цикл публикаций, модерацию, ответы, поиск, лайки, избранное, категории, профиль, пароль, загрузку изображений и импорт старых данных, затем останавливает кластер. Не обращается к базе из backend/.env. Тестовые файлы остаются в системном временном каталоге для диагностики.

## Пользовательские публикации и проверка редакцией

После обновления выполните npm run migrate из backend. Команда применит версионированную миграцию 002_article_submissions одной транзакцией и запишет её в schema_migrations. Повторный запуск безопасен. Миграция добавляет поля и таблицу версий, расширяет допустимые статусы и не удаляет существующих пользователей, статей или комментариев.

Обычный пользователь регистрируется через /register и входит через /login. Публичная регистрация всегда создаёт роль user; передать admin невозможно. Существующие роли ADMIN и USER хранятся как admin и user для совместимости с текущей авторизацией.

После входа доступны «Предложить новость» (/my/posts/create) и «Мои публикации» (/my/posts). Форма включает название, описание, текст, категорию, ссылку на изображение или загрузку файла. Материал можно сохранить как draft или отправить в PENDING_REVIEW. Статус, автор и проверяющий не принимаются от пользователя. Черновики и отклонённые версии можно редактировать и отправлять повторно. Версию на проверке пользователь не редактирует до решения редакции.

В панели администратора раздел «Новости на проверке» (/admin/submissions) показывает очередь отправок. Редактор читает сохранённую исходную отправку, редактирует рабочую версию и нажимает «Одобрить и опубликовать» либо «Отклонить». Причина отклонения необязательна и видна автору. Правки и одобрение выполняются атомарно; два одновременных окончательных решения не могут изменить одну и ту же версию.

### Авторство и повторные версии

Поле author_user_id — хранимый генерируемый столбец из существующего author_id. Старые импорты и API остаются совместимыми. Триггер PostgreSQL запрещает изменение author_id после создания статьи. Поля reviewed_by_admin_id и reviewed_at отдельно фиксируют администратора и время решения.

post_revisions хранит рабочие версии и неизменяемый original_submission каждой отправки. Отклонённые отправки не перезаписываются: новая отправка получает новую версию. При редактировании опубликованной статьи пользователь создаёт отдельный draft. Текущий опубликованный текст остаётся на сайте, пока администратор не одобрит новую версию. Отклонение новой версии не скрывает прежнюю публикацию. ID статьи, slug, комментарии, лайки и избранное сохраняются.

Публичный сайт показывает «Автор: Алия», даже если материал редактировал и публиковал администратор. API связывает автора с author_user_id; модератор никогда не назначается автором при проверке.

### API отправок

| Маршрут | Доступ и поведение |
|---|---|
| GET /api/my/posts | Только свои статьи; page, limit, status |
| POST /api/my/posts | title, summary, content, category, image; необязательные tags и intent=draft/submit. По умолчанию submit → PENDING_REVIEW |
| GET /api/my/posts/:id | Собственная статья, актуальная версия и история |
| PUT /api/my/posts/:id | Только собственный draft, rejected или новая версия published; передача status/author запрещена |
| POST /api/my/posts/:id/submit | Пустой JSON; сервер переводит версию в PENDING_REVIEW |
| POST /api/my/upload | Загрузка изображения автором; multipart поле image, до 5 МБ |
| GET /api/admin/submissions | Очередь PENDING_REVIEW; page, limit |
| GET /api/admin/submissions/:revisionId | Исходная и редакционная версии |
| PUT /api/admin/submissions/:revisionId | Правки текущей версии на проверке |
| PATCH /api/admin/submissions/:revisionId/decision | decision=approve/reject, необязательный reason. changes позволяет атомарно применить правки при решении |

Все административные маршруты защищены существующими protect и admin. Для чужой собственной статьи /api/my возвращает 404. Для обычного пользователя административные маршруты возвращают 403, без токена — 401. Старый PUT /api/admin/news/:id при публикации ожидающей версии также выполняет редакционное решение и сохраняет автора. Неотправленные пользовательские черновики через него опубликовать нельзя.
